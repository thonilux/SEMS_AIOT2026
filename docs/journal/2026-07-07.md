## 1. Preset Register Map — Renata AX9L 3-Phase

### Konteks
Selain PM2xxx/EM6400 (FP32), muncul kebutuhan support meter **Renata AX9L** — format register beda total: `long` (INT32 signed, bukan float) + scale factor per parameter (0.1V, 0.001A, dst), alamat pakai konvensi Modicon hex (`0x4000` dst).

### Implementasi Firmware
- `ModbusConfig.meterType` baru: `0` = FP32 (PM2xxx/EM6400), `1` = INT32+scale (Renata AX9L)
- `bytesToLong()` — decode big-endian signed int32
- Macro `MB_READ_L(field, reg, scale)` — baca 2 register, decode long, kali scale
- `handleModbus()` 3-phase sekarang 3-way branch: FP32 (PM2xxx) vs INT32+scale (Renata) sesuai `meterType`
- Vll/Vln/Iavg di-skip untuk Renata (gak ada di register map-nya)
- Web UI `/modbus`: tombol preset baru **"Renata AX9L — 3-Phase (INT32)"**, radio eksplisit **"Tipe Data Register"** (FP32 vs INT32+Scale) — sebelumnya cuma keset via JS variable dari tombol preset, gak ada kontrol visible, jadi ditambah radio manual
- NVS: field `type` baru disimpan/dimuat dari namespace `modbus`

### Alamat Register Renata (hex Modicon → desimal dipakai firmware)
| Param | Hex | Desimal | Scale |
|---|---|---|---|
| Va/Vb/Vc | 0x4000/02/04 | 16384/86/88 | 0.1 V |
| Ia/Ib/Ic | 0x400C/0E/10 | 16396/98/16400 | 0.001 A |
| Pa/Pb/Pc/Ptot | 0x4012–18 | 16402–16408 | 0.1W → kW (×0.0001) |
| Qa/Qb/Qc/Qtot | 0x401A–20 | 16410–16416 | sama pola, kvar |
| Sa/Sb/Sc/Stot | 0x4022–28 | 16418–16424 | sama pola, kVA |
| PFa/PFb/PFc/PFtot | 0x402A–30 | 16426–16432 | 0.001 |
| Freq | 0x4032 | 16434 | 0.01 Hz |
| Energy (Active) | 0x4034 | 16436 | 0.01 kWh |

## 2. Root Cause — Framing Serial Salah (8E1 vs 8N2)

### Masalah
Preset Renata udah diterapkan, tapi data tetap gak kebaca sama sekali dari meter.

### Investigasi
User kasih script python `ax9l.py` yang **sudah terbukti jalan** di lapangan. Dipelajari detail:
- `decode_register_32()`: signed int32 big-endian — cocok sama `bytesToLong()` yang udah dibuat
- Register map & scale — cocok 100% sama yang sudah diimplementasi
- **`ModbusSerialClient(..., stopbits=2, bytesize=8, parity='N', ...)`** — ini beda dari asumsi awal!

Firmware hardcode `Serial2.begin(modbusCfg.baud, SERIAL_8E1, ...)` — **8E1** (parity Even, 1 stop bit), padahal Renata AX9L butuh **8N2** (no parity, 2 stop bit). PM2xxx/Schneider memang defaultnya 8E1, tapi Renata beda protokol serial di level UART framing — bukan soal decode/scale sama sekali.

### Fix
```cpp
uint32_t rs485Config = (modbusCfg.meterType == 1) ? SERIAL_8N2 : SERIAL_8E1;
Serial2.begin(modbusCfg.baud, rs485Config, kRs485Rx, kRs485Tx);
```
Framing dipilih otomatis sesuai `meterType`, aktif setelah reboot (banner UI diperbarui: "Perubahan baud rate & tipe meter aktif setelah reboot").

Preset Renata juga auto-set baud ke **9600** (default `ax9l.py`, beda dari default PM2xxx 19200) — sebelumnya preset cuma isi alamat register, baud dropdown gak ikut ke-set.

## 3. Fitur Baru — Ping Register (Debug Tool)

### Kenapa Perlu
Setelah fix framing, tetap ada laporan "gak kebaca". Debug lewat serial monitor gak bisa karena device diakses **cuma via OTA** (USB gak konek). Perlu cara diagnosa low-level tanpa serial.

### Implementasi
- `modbusPing()` — baca 1 register manual, return raw bytes + error spesifik (bukan cuma bool):
  - Timeout total (0 byte balik)
  - Respon kependekan (framing salah)
  - CRC mismatch (parity/stopbit gak cocok)
  - Slave ID beda
  - Modbus exception code (alamat register salah)
- Endpoint `GET /api/modbus/ping?addr=&slave=&scale=` — return JSON `{ok, raw, asFloat, asLong, asLongScaled}` atau `{ok:false, error}`
- Web UI `/modbus`: card baru **"Test Koneksi (Ping Register)"** — input slave ID + alamat, tombol Ping, hasil ditampilkan langsung (raw hex + 2 interpretasi)

## 4. Diagnosa Bertahap — Ternyata Bus Contention

### Kronologi Debug
1. Ping dari firmware → **timeout total**, 0 byte balik, walau framing & baud udah benar
2. Dicek fisik: A/B udah dibolak-balik, tetap gagal, TX LED kedip (request beneran keluar)
3. Curiga hardware DE/RE (modul RS485 manual vs auto-direction) — user cek schematic
4. **Breakthrough**: dibuatkan ESPHome test config (`docs/labiot2026_ax9l.yaml`) sebagai sniffer pasif (`uart.debug`, `dummy_receiver: true`) — cuma dengerin bus, gak kirim apa-apa
5. Sniffer nangkep traffic **python `ax9l.py` yang jalan bersamaan di Ubuntu** (USB-RS485 kedip) — request/respon slave 2 & 3 **valid sempurna** (CRC cocok, byteCount 128 byte = 64 register). Slave 1 gak pernah dibales (device gak ada/mati)
6. Ini membuktikan: wiring, baud, parity, dan meter itu sendiri **semua sehat** — problem bukan di situ

### Kesimpulan
**Modbus RTU cuma boleh 1 master aktif di bus.** Selama python Ubuntu polling terus-menerus, request dari device kita (siapapun masternya — firmware atau ESPHome) tabrakan di bus dan gak pernah dapat respon bersih. Bukan bug kode.

## 5. Isolasi Lanjut — ESPHome Sebagai Master (USB Ubuntu Dicabut)

Setelah `ax9l.py` dimatikan, config `docs/labiot2026_ax9l.yaml` diubah balik dari sniffer jadi master aktif (`modbus_controller`, slave 2), sambil tetap log raw traffic via `uart.debug`.

### Hasil Percobaan 1 (board Ethernet W5500)
ESPHome kirim request valid (CRC benar, alamat bervariasi 0x4000/0x400C/0x4018/dst) tapi **tetap 0 respon** — beda total dari waktu cuma jadi sniffer (yang berhasil nangkep traffic Ubuntu).

### Analisa
RX jalan normal (kebukti sniffer), tapi **TX gak pernah nyampe ke bus fisik**. Kandidat:
- Rangkaian isolasi TX (opto-coupler `XL-2H12SURC`) di jalur TXD → mati/salah pasang
- Sinyal RE/DE dari `74HC04` (auto-direction) gak toggle HIGH pas transmit — MAX485 permanen di mode receive

User cek pakai multimeter, ketemu bacaan **DE/RE minus** — kemungkinan ground referensi ketuker (desain ini pakai opto-isolator, GND sisi MAX485 kemungkinan beda domain dari GND ESP32/logic) atau probe kebalik.

### Hasil Percobaan 2 (board WiFi, bukan Ethernet)
Config sama (`docs/labiot2026_ax9l_wifi.yaml`, SSID `EMJI`) di-flash ke **board WiFi** — **berhasil baca data!**

Kemungkinan penyebab bedanya:
1. Board WiFi ini fisiknya beda (rangkaian RS485/isolasi lain, gak ada masalah DE/RE)
2. Atau simply karena `ax9l.py` di Ubuntu udah dimatikan permanen pas test kedua ini (bus contention dari poin 4 udah hilang, bukan soal WiFi vs Ethernet sama sekali)

**Belum dipastikan mana penyebab sebenarnya** — perlu tes ulang board Ethernet W5500 dalam kondisi Ubuntu python OFF total buat isolasi variable.

## 8. Root Cause Final Board Ethernet W5500 — TVS/Fuse, Bukan Chip Aktif

### Koreksi
Komponen `XL-2H12SURC` di schematic bagian tengah **bukan opto-isolator** — cuma LED indikator TX/RX biasa. Desain ini gak pakai isolasi galvanic sama sekali; dugaan opto rusak di poin 5 keliru, dibatalkan.

### Urutan Debug Fisik (Trial & Error Terarah)
| Langkah | Aksi | Hasil |
|---|---|---|
| 1 | Balik polaritas zener/TVS | Gak ngaruh |
| 2 | Ganti chip 74HC04 | Gak ngaruh |
| 3 | Ganti chip MAX485 | Gak ngaruh |
| 4 | Copot TVS (D2/D3/D8) + jumper fuse F3/F4 | **TX langsung lancar** |
| 5 | Balikin MAX485 **awal** (bukan pengganti) | Tetap lancar |
| 6 | Balikin 74HC04 **awal** (bukan pengganti) | Tetap lancar |

### Kesimpulan
**Root cause: TVS diode atau fuse (F3/F4) yang gagal/rusak** di jalur A/B — bukan MAX485, bukan 74HC04, bukan firmware. Kemungkinan TVS short atau fuse (PPTC) putus akibat kejadian sebelumnya (short/overcurrent/ESD), meng-clamp atau memutus jalur sinyal sehingga TX gak pernah nyampe ke bus meski chip driver-nya sendiri sehat total.

Chip MAX485 dan 74HC04 **original** ternyata tidak pernah rusak — penggantian chip di langkah 2–3 sebelumnya adalah dead-end, tapi berguna buat eliminasi sistematis sebelum ketemu komponen pasif yang beneran jadi biang keladi.

### Ganti TVS Baru — Ternyata Soal Polaritas, Bukan Cuma Part Rusak

Part TVS dikonfirmasi benar: **SMAJ6.5A** (Microdiode Semiconductor, marking `MDD 31F AK`), unidirectional, DO-214AC/SMA. Karena unidirectional, orientasi (katoda/anoda) krusial.

Verifikasi katoda pakai multimeter mode diode-test: probe hitam di garis body → kebaca ~0.5V (forward) → **konfirmasi garis body = katoda**, sesuai konvensi standar marking.

**Percobaan 1** — D2 & D3 dipasang katoda→A/B (sinyal), anoda→GND (asumsi textbook standar proteksi RS485) → **TX macet lagi**.

**Percobaan 2 (Fix Final)** — D2 & D3 **dibalik**: katoda→GND, anoda→A/B (kebalikan dari konvensi textbook) → **TX lancar**.

**Kesimpulan orientasi board ini:** desain proteksi di board ini pakai orientasi **katoda-ke-GND** untuk D2/D3 (bukan katoda-ke-sinyal seperti kebanyakan app-note generik). Kemungkinan besar TVS yang gagal dari awal itu rusak karena beda antara orientasi asli pabrik (katoda-ke-GND) vs asumsi yang dipakai saat replacement pertama — pelajaran: jangan asumsi konvensi umum tanpa verifikasi/trial di board spesifik.

D8 (A↔B, line-to-line) belum dipastikan — gak ada rujukan GND buat pola yang sama. Rencana: pasang salah satu arah dulu (coba katoda→B), tes TX; kalau gagal, balik ke katoda→A.

### Next Steps
- Tentukan orientasi final D8 lewat trial (katoda→B dulu, baru →A kalau gagal)
- Dokumentasikan orientasi final semua 3 TVS (D2/D3/D8) di schematic biar gak keulang salah pas replacement berikutnya
- Setelah fix permanen semua, re-test board Ethernet W5500 dengan firmware utama (bukan cuma ESPHome) buat konfirmasi akhir
