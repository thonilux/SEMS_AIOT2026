## Sesi Ini — Web UI Features + Web Server Debugging

### Fitur yang Berhasil Diimplementasi

#### Config Mode (GPIO0 BOOT button, hold 3s)

- `handleConfigButton()` polling setiap loop, deteksi hold ≥ 3000ms
- `enterConfigMode()` → set `rtcConfigMagic = 0xC0FEF00D` → `ESP.restart()`
- Boot berikutnya deteksi magic → masuk `WIFI_AP` only (STA radio off)
- OLED: "Config Mode / Restarting..."
- Web UI: tombol "Config Mode (AP)" di halaman root → `POST /api/config-mode`

**Bug saat implementasi:** Magic constant `0xC0NFFEED` — `N` bukan hex valid → compiler error. Diganti `0xC0FEF00D`.

**Bug lain:** Config mode sempat run normal setelah reboot. Root cause: branch `wifiCount > 0` di setup() triggered sebelum cek `configModeReboot`, sehingga STA connect tetap jalan. Fix: pindahkan cek `configModeReboot` ke posisi paling atas dengan `WiFi.mode(WIFI_AP)` (bukan AP_STA), sehingga STA radio benar-benar off.

#### Fail Count di OLED

- `RTC_DATA_ATTR static uint32_t rtcWifiFailCount` — survive reboot, reset saat power-off
- Setiap `scheduleReboot()` → `rtcWifiFailCount++`
- OLED tampilkan "Gagal #N" di baris ketiga overlay No WiFi

#### AP Tidak Broadcast saat WiFi Kosong — Fix

Kondisi: fresh boot, tidak ada saved WiFi, AP tidak aktif. Root cause: branch `wifiCount == 0` tidak memanggil `startAp()`. Fix: tambah `startAp()` di branch itu juga.

#### Postpone Reboot jika AP Client Konek

Di `handleRebootCountdown()`, sebelum `ESP.restart()`:
```cpp
if (WiFi.softAPgetStationNum() > 0) {
  rebootAtMs = now + 30000;  // tunda 30 detik
  ...
}
```
Kalau client masih konek ke AP (sedang config), reboot ditunda 30 detik. Bisa tunda berkali-kali.

#### OLED Notifikasi saat Web UI Dibuka

Setiap handler halaman (`handleRoot`, `handleNetworkPage`, `handleMqttPage`) memanggil:
```cpp
oledShow("Web UI", "Setup dibuka", server.client().remoteIP().toString().c_str(), 3000);
```
OLED tampilkan IP client selama 3 detik.

#### Form "Tambah WiFi" di Root Page (kemudian dihapus)

Sempat ditambahkan form input SSID + password langsung di `/` karena user tidak bisa menemukan form di `/network`. Tapi ini membuat tampilan dashboard berantakan dan scan WiFi hilang dari flow. Akhirnya dihapus — semua manajemen WiFi dikembalikan ke `/network`.

## Kegagalan Web Server — Kronologi Lengkap

### Background: Tujuan Awal

User ingin web UI bisa diakses dari **WiFi dan LAN (W5500) sekaligus**, atau minimal LAN-priority (kalau LAN up, serve dari LAN; kalau tidak, pakai WiFi). Ini yang memicu serangkaian percobaan.

---

### Percobaan 1: ETH.h untuk W5500 SPI (LAN priority WebServer)

**Tujuan:** Daftarkan W5500 ke lwIP stack via `ETH.h` supaya `WebServer` bisa listen di kedua interface.

**Hasil: GAGAL**

Error:
```
no matching function for call to 'ETHClass::begin(...)'
'SPI3_HOST' was not declared in this scope
```

**Root cause:** Framework `3.20017.241212` (arduino-esp32 versi lama). `ETH.h` di versi ini hanya support RMII/MII (Ethernet chip built-in di ESP32). Tidak ada overload `begin()` untuk W5500 SPI. Fitur ini baru tersedia di arduino-esp32 v3.x ke atas (ESP-IDF 5.x based).

**Keputusan:** Rollback — W5500 tetap pakai `Ethernet_Generic`, bukan `ETH.h`.

---

### Percobaan 2: ESPAsyncWebServer — Attempt 1

**Library:**
```ini
esphome/AsyncTCP-esphome @ ^2.1.4
esphome/ESPAsyncWebServer-esphome @ ^3.3.0
```

**Tujuan:** Async server tidak terikat satu interface seperti sync `WebServer`.

**Crash pertama:** `tcpip_send_msg_wait_sem Invalid mbox`

Root cause: `startWebServer()` dipanggil sebelum `WiFi.mode()` di setup(). lwIP mailbox belum diinisialisasi saat `server.begin()` dipanggil.

Fix: Pastikan urutan di setiap branch setup():
```cpp
WiFi.mode(WIFI_AP);     // HARUS dulu
startAp();
startWebServer();       // baru ini
```

**Hasil setelah fix crash:** Firmware boot normal, WiFi connect, Serial log normal — tapi browser tetap **"connection refused"**. Tidak ada TCP handshake sama sekali.

**Yang sudah dicoba untuk debug:**
- Ganti ke local network switch tanpa internet → tetap refused
- Coba ping IP ESP32 (tidak didokumentasikan hasilnya)
- Tidak ada error di Serial saat browser connect

**Root cause yang diduga tapi tidak dikonfirmasi:** AsyncTCP kemungkinan bind ke interface yang pertama aktif saat `begin()` dipanggil. Di saat itu WiFi STA belum dapat IP (masih connecting), sehingga AsyncTCP tidak properly listen di interface manapun.

---

### Percobaan 3: ESPAsyncWebServer — Attempt 2 (fresh WiFi clear)

**Konteks:** User tidak bisa akses web UI untuk clear saved WiFi. Solusi sementara: tambah `clearAllWifi()` hardcode di `setup()`, upload, jalankan sekali, upload lagi tanpa itu.

Setelah WiFi di-clear dan ESP32 boot ke AP mode (no saved WiFi → AP aktif langsung):

**Hasil: tetap "connection refused"** meskipun:
- ESP32 di AP mode (IP 192.168.4.1, tidak ada STA connecting)
- Client konek ke AP ESP32 langsung
- Seharusnya tidak ada race condition interface

**Kesimpulan:** ESPAsyncWebServer tidak berfungsi di setup ini. Bukan masalah timing atau interface race. Kemungkinan incompatibility antara versi library esphome dengan framework arduino-esp32 `3.20017`.

---

### Percobaan 4: ESPAsyncWebServer — Masalah UI (form WiFi hilang)

Masalah terpisah dari koneksi. Saat form "Tambah WiFi" dipindah ke halaman root (`/`):
- Scan WiFi hanya ada di `/network` (pakai `kScanScript` PROGMEM shared)
- Root page tidak punya JS scan, sehingga user tidak bisa scan dari dashboard
- Flow membingungkan: user di `/` tapi harus ke `/network` untuk scan

Fix: Hapus form dari root, kembalikan semua flow WiFi ke `/network`. Root page hanya tampilkan info + link navigasi.

---

### Rollback ke `WebServer` (2026-06-21)

**Keputusan:** Buang ESPAsyncWebServer, kembali ke `WebServer` Arduino built-in yang **sudah terbukti kerja** sebelum sesi ini.

**Perubahan kode:**

| Sebelum (Async) | Sesudah (Sync) |
|---|---|
| `#include <ESPAsyncWebServer.h>` | `#include <WebServer.h>` |
| `static AsyncWebServer server(80)` | `static WebServer server(80)` |
| `void handler(AsyncWebServerRequest* req)` | `void handler()` |
| `req->send(200, ...)` | `server.send(200, ...)` |
| Body dari `uint8_t* data, size_t len` | Body dari `server.arg("plain")` |
| Handler POST body: 5-param lambda | `server.on("/path", handler)` langsung |
| Tidak perlu `handleClient()` | `server.handleClient()` di setiap `loop()` |

Helper ekstrak JSON dibuat jadi fungsi sendiri karena dipakai di beberapa handler:
```cpp
static String jsonExtract(const String& body, const char* key);
```

**Build:** Sukses, 900KB (turun dari 924KB saat async).

**Status saat jurnal ini ditulis:** Baru di-upload, belum dikonfirmasi bisa diakses via browser.

## Catatan Teknis Penting Sesi Ini

### Kenapa ESPAsyncWebServer Gagal

Tidak ada error eksplisit — firmware tidak crash, koneksi TCP-nya yang tidak terbentuk. Kemungkinan penyebab: library esphome variant AsyncTCP tidak kompatibel dengan framework `3.20017`. Solusi yang tepat seharusnya upgrade framework ke ≥3.1.0 (ESP-IDF 5.x), tapi itu risiko besar menjelang deadline B4T.

### Kenapa `WebServer` Sync Dipilih Kembali

- Sudah terbukti kerja di setup ini
- Tidak ada kebutuhan concurrent connection (satu user config pada satu waktu)
- `handleClient()` di loop tidak menimbulkan masalah karena tidak ada operasi blocking lain di loop yang lama
- Lebih predictable untuk debugging

### Constraint Deadline

B4T Juli 2026 — prioritas adalah firmware yang **stabil dan bisa dikonfigurasi**, bukan fitur tambahan. Web UI harus kerja dulu sebelum lanjut ke Modbus.
