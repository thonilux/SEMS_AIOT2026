## 5. Port Relay Control (dari branch `renatta-ax9l-single-phase`)

Fungsi relay 4-channel di-port dari `https://github.com/thonilux/SEMS_AIOT2026/blob/renatta-ax9l-single-phase/firmware/src/main.cpp`, diadaptasi ke gaya flat-struct `main.cpp` sekarang (bukan `ConfigManager`/`PinMap` class pattern branch asal).

**MQTT sesuai spesifikasi payload gist tim hardware** (`https://gist.github.com/AlfandiMario/7856b8564bf53e7d410d33f1c1666fb6`):
- Command: `trofis/enms/demo-sems/control/relay_<1..4>` — subscribe, raw byte `"0"`/`"1"`, QoS1
- State: `.../relay_<N>/state` — publish, retained, republish saat command diterima/boot/reconnect/trip/auto-retry

Fitur: state machine OFF/ON/TRIP, overcurrent protection, auto-retry setelah trip, GPIO pin configurable (default 2/15/14/13), persist NVS namespace `"relay"`. Web `/relay` page + API `/api/relay/state`, `/api/relay/set`, `/api/relay/config`.

### Bug ditemukan & fixed: GPIO2 heartbeat vs Relay 1

GPIO2 dobel fungsi — default LED heartbeat pin **dan** default Relay 1 pin. Loop heartbeat (`digitalWrite(kLedPin, ...)` tiap 500ms) menimpa state relay tanpa guard. Fix: skip heartbeat write kalau GPIO2 sedang diklaim relay manapun.

## 6. Multi-PM (Multi Power Meter) — 4-Slot Array

Kebutuhan: Renata AX9L (1-phase) + Schneider PM2120 (3-phase) polling simultan. Dikerjakan 3 tahap sekuensial (setiap tahap verified build sebelum lanjut, karena percobaan single-pass sebelumnya bailed akibat scope terlalu besar):

1. **Struct + round-robin poll** — `MeterSlotConfig[4]` + `MeterSlotResult[4]`. Slot 0 = Renata AX9L (block-read FC03 0x4000×34 + 0x4022×30, INT32, 9600 8N2). Slot 1 = Schneider PM2120 (register map existing, FP32, 19200 8E1). Slot 2/3 reserve.
2. **NVS persist + MQTT per-slot** — config per-slot reboot-proof, topic awal `<prefix>/<deviceId>/meter_<N>`.
3. **Web UI multi-slot** — `/modbus` jadi 4 kartu, live status, config form per-slot, advanced register-map collapsed by default (hemat Flash — headroom cuma ~61KB saat itu).

Build final tahap ini: RAM 17.2%, Flash 94.9%.

### Verifikasi register map Renata AX9L via datasheet resmi

User share tabel datasheet AX9L — semua alamat register (voltage/current/power/PF/frequency/energy, 0x4000–0x4034) dicocokkan dan **match persis** dengan yang sudah di-port. Dikonfirmasi: Renata AX9L pakai register map identik untuk mode 1-phase maupun 3-phase (beda cuma jumlah kabel fisik yang disambung), sehingga pendekatan "baca selalu 3-phase-shaped, publish bisa pilih shape 1P" itu valid sesuai datasheet.

## 11. Partition Table 16MB

User mengonfirmasi varian board fisik yang dipakai punya **16MB flash**, bukan 4MB default board `esp32dev`. Dibuat `firmware/partitions_16mb.csv` (dual OTA, app slot 6MB masing-masing, NVS 64KB, spiffs 3.9MB, coredump 64KB), `platformio.ini` di-set `board_build.flash_size/partitions`.

Build compile-time: Flash turun dari **95.2% → 19.8%** — headroom jauh lebih lega untuk fitur ke depan.

**Catatan penting:** OTA (`/update`) hanya menulis app slot, **tidak** menulis ulang bootloader + partition table (offset 0x8000). Percobaan OTA dengan partition table baru dilakukan atas keputusan sadar-risiko user — device survive, config tidak corrupt, tapi kemungkinan besar partition table fisik **belum benar-benar aktif** di device sampai dilakukan **flash penuh via USB** (`pio run -t upload`). Ditunda sampai device bisa diakses fisik.

## 13. Bagian Lanjutan — Debugging Hardware Live & Fitur MQTT Lanjutan

Setelah commit `ddcc901`/`c39184e`, sesi berlanjut dengan device fisik tersambung (IP LAN berubah-ubah: `192.168.1.17` → `192.168.1.2` seiring DHCP lease/reboot). Fokus bergeser dari fitur baru ke **debugging langsung di hardware** dan penyempurnaan sesuai kebutuhan lapangan.

### 13.1 GPIO2 Heartbeat vs Relay 1 — Bug Nyata Ditemukan & Fixed

User laporan: relay masih "heartbeat" (berkedip) walau seharusnya statis. Root cause: GPIO2 dipakai ganda — default LED heartbeat pin **dan** default Relay 1 pin (`kRelayDefaultPins[0] = 2`). Loop heartbeat (`digitalWrite(kLedPin, ...)` tiap 500ms) menimpa state relay tanpa guard.

**Fix:** skip heartbeat write kalau GPIO2 sedang diklaim relay manapun (loop cek `relayCfg.pin[i] == kLedPin`).

### 13.2 Config Mode "Tidak Jalan" — Ternyata Bukan Bug

User laporan: config mode tidak aktif, device selalu masuk Normal Mode. Investigasi: device sebenarnya **sudah** di Config Mode (AP `SEMS-SETUP-xxxxxx` aktif di `192.168.4.1`), tapi tetap bisa diakses via IP LAN normal (LAN-first boot) sehingga user mengira ini Normal Mode. Root cause sebenarnya: WiFi "EMJI" sudah tersimpan dari testing sebelumnya dan berhasil connect — begitu STA connect sukses, sistem otomatis Normal Mode (bukan bug, itu behavior benar).

**Bug sungguhan yang ditemukan selama investigasi ini** (di luar laporan awal, tapi nyata): `startAp()`/`restoreAp()` tidak pernah mengecek return value `WiFi.softAP()` — kalau radio gagal broadcast, `apStarted` tetap di-set `true` sehingga `/api/network` melaporkan status AP palsu (`active:true` padahal tidak benar-benar broadcast). **Fix:** cek return value, retry sekali dengan delay 300ms, log kegagalan eksplisit, dan `apStarted` hanya `true` jika `softAP()` benar-benar berhasil.

### 13.3 Bug Sequential Modbus Read — Fixed (Root Cause Sebenarnya dari "Modbus Tidak Bisa")

User laporan meter Schneider (id=3) dan Renata 1P (id=2, 19200 8E1) tidak terbaca. Setelah serangkaian tes (ping single-register vs poll penuh), ditemukan: **setiap register individu berhasil dibaca via ping**, tapi **poll penuh (22 request FC03 beruntun) selalu gagal**. Root cause: `MB_READ`/`MB_READ4Q` macro di `pollSchneiderSlot()` tidak punya delay antar-request — device (khususnya Schneider PM2120 unit ini) butuh silent-interval sebelum siap menerima frame Modbus berikutnya; tanpa jeda, salah satu dari ~22 request beruntun gagal decode dan `ok=false` membatalkan seluruh hasil poll (all-or-nothing).

**Fix:** tambah `delay(15)` di awal setiap `MB_READ`/`MB_READ4Q`. Setelah fix, Schneider langsung `online:true valid:true`.

### 13.4 Single Bus-Wide Baud/Parity (Refactor dari Per-Slot)

User minta: satu konfigurasi baud+parity untuk seluruh bus RS485 (bukan per-slot) — karena secara fisik `Serial2` cuma bisa satu framing aktif sekaligus, jadi per-slot baud selama ini semu.

**Perubahan:**
- Field `baud` dihapus dari `MeterSlotConfig`, diganti `BusConfig busCfg` global (`baud` + `parity`, 0=8N1/1=8E1/2=8O1/3=8N2), NVS namespace baru `"bus"`.
- `Serial2` di-init sekali di `setup()`, tidak lagi di-reconfigure tiap poll cycle.
- Endpoint baru `POST /api/bus/save` — apply langsung tanpa reboot.
- Web UI `/modbus`: panel baru "RS485 Bus (semua slot)", dropdown Baud Rate per-slot dihapus dari form edit slot.

### 13.5 Debugging Hardware Marathon: Renata AX9L Tidak Terbaca

Sesi debugging panjang dan iteratif untuk Renata AX9L yang konsisten timeout total (tidak ada respons sama sekali) di semua kombinasi slave ID (1-5, 10, 247), semua address, dua baud/parity (19200 8E1 dan 9600 8N1). Langkah-langkah yang dicoba:

1. Ping diagnostic per-register — confirm bukan salah address.
2. Cabut Schneider dari bus (isolasi bus contention) — Renata tetap timeout, Schneider sendirian tetap sukses respons di bus yang sama → confirm bus/wiring dari sisi ESP32 sehat.
3. Cek fisik: power, GND kontinuitas, slave ID di layar — user konfirmasi semua sudah benar.
4. Hipotesis resettable fuse (PTC) — power-cycle Renata total. Tidak membantu langsung.
5. **Swap kabel A/B (tukar polaritas)** + ubah slave ID device fisik ke 1 — **berhasil!** `slave=1` merespons dengan data valid (`asLong:2166`).
6. Sempat regresi (kolaps total lagi) setelah Schneider disambung ulang — ternyata bukan karena Schneider, tapi karena user juga mencabut kabel power lain bersamaan saat proses sambung-cabut (device ESP32 sempat reboot, `uptime` 45 detik saat dicek).
7. Setelah recovery, Schneider di-set ulang ke `slave=2` (dari `slave=3` sebelumnya) — sukses dengan bug sequential-read yang sama (lihat 13.3), di-fix bersamaan.

**Kesimpulan:** kombinasi kabel A/B yang salah polaritas (device tetap "hidup" secara listrik tapi tidak pernah decode sinyal RS485 dengan benar) adalah akar masalah utama. Setelah swap + slave ID disesuaikan, kedua meter (Renata slave=1, Schneider slave=2) online stabil di bus 9600 8N1.

Sempat disiapkan `docs/esphome-ax9l-diag.yaml` sebagai rencana tie-breaker test independen (ESPHome modbus_controller, battle-tested, untuk isolasi bug software vs hardware) — pada akhirnya tidak diperlukan karena hardware fix (swap kabel) sudah menyelesaikan masalah sebelum config ini dijalankan. File tetap disimpan di repo sebagai referensi diagnostic tool untuk kasus serupa di masa depan.

### 13.6 Bug Kritis: Urutan Topic MQTT Terbalik (Ditemukan dari Screenshot Dashboard)

User share screenshot halaman admin dashboard (`demo.sems.web.id/devices`) yang menunjukkan field "MQTT Topic" pada device terkonfigurasi: `trofis/enms/demo-sems/elc_data/slave_1` — pola **elc_data lebih dulu, baru slave_N**.

Firmware saat itu publish ke `<mqttTopic>/elc_data` dengan `mqttTopic` berisi full path termasuk `slave_N` di ujung — hasil akhir: `trofis/enms/demo-sems/slave_1/elc_data`, **urutan terbalik** dari yang dashboard subscribe. Ini menjelaskan kenapa data terkirim (device-side logic sudah benar, `mqttPostCount` naik) tapi tidak pernah muncul di dashboard.

**Fix — field dipecah dua:**
- `mqttTopic` (base path saja, mis. `trofis/enms/demo-sems`)
- `mqttSuffix` baru (identitas per-meter, mis. `slave_1`/`slave_2`)
- Topic final disusun benar: `<mqttTopic>/elc_data/<mqttSuffix>` dan `<mqttTopic>/elc_wh/<mqttSuffix>`

**Bug kedua yang ditemukan bersamaan:** field `slave_id` di body payload memakai `cfg.slaveId` (alamat Modbus RTU fisik), bukan angka dari suffix topic gist — padahal spek eksplisit menyatakan *"`slave_id` di body tetap diisi biar konsisten [dengan topic]"*. Ditambahkan `gistIdFromSuffix()` yang mengekstrak angka dari `mqttSuffix`, dipakai di seluruh payload (`elc_data` dan `elc_wh`).

Web UI `/modbus` diperbarui: satu field "MQTT Topic" jadi dua field terpisah ("MQTT Base Topic" + "MQTT Suffix"), dengan keterangan pola publish di bawahnya.

### 13.7 Fix Firmware Default (Bukan Cuma Runtime API)

Dua masalah lapangan ditemukan dan sengaja di-fix di level **firmware default** (bukan cuma via API runtime), atas permintaan eksplisit user supaya persist konsisten walau device di-reset/reflash:

- **Relay terbalik** — modul relay fisik ternyata active-LOW, sementara `RelayConfig.activeHigh` default `true`. Diubah default jadi `false` (di struct definition dan fallback NVS `getBool`).
- **Poll RS485 terlalu sering** — default `pollMs` per slot dinaikkan dari `1000` ke `3000` (siklus round-robin penuh 2 slot: ~2 detik → ~6 detik), mengurangi beban bus.
- Sekalian disinkronkan: default `slaveId` seed (Renata=1, Schneider=2) dan default `BusConfig` (9600/8N1) diubah agar cocok dengan konfigurasi fisik yang sudah terbukti jalan — sebelumnya default masih menyisakan nilai lama (19200/8E1, slaveId 2/3) yang berbeda dari kondisi lapangan aktual.

### 13.8 Fitur Baru: Publish MQTT Terjadwal RTC (Bukan Interval Bebas)

Permintaan: `elc_wh` (energi kWh) dipublish pada detik spesifik per meter berdasarkan RTC — PM1 di `hh:mm:01`, PM2 di `hh:mm:02`, dst. Setelah klarifikasi, `elc_data` (real-time V/I/P) punya pola berbeda: 3x per menit di `hh:mm:0x`, `hh:mm:2x`, `hh:mm:4x` (x = index slot + 1).

**Implementasi:**
- `publishMeterSlot()` dipecah jadi dua fungsi independen: `publishElcData(i)` dan `publishElcWh(i)`.
- `publishMeter()` ditulis ulang sebagai RTC-based scheduler: tiap slot dicek terhadap detik target (`slotSec = (i+1) % 60`), dengan dedup guard (`lastPublishedDataSec[]`/`lastPublishedWhSec[]`) agar tidak fire berulang selama detik yang sama masih berjalan.
- **Fallback**: jika NTP belum sync, otomatis pakai skema interval lama (`kMeterPublishMs`) supaya data tetap mengalir sebelum RTC tersedia, baru berpindah ke jadwal presisi-detik begitu sync.

- **Hardware debugging RS485 butuh pendekatan sistematis isolasi variabel satu-per-satu**: cabut device lain (isolasi bus contention), swap polaritas kabel, ganti slave ID, power-cycle — masing-masing menyingkirkan satu kemungkinan penyebab. Kunci solusinya (swap A/B) baru ketemu setelah kombinasi lain (baud, parity, slave ID sendirian) semua dicoba habis.
- **"Semua register individu berhasil dibaca, tapi baca sekaligus gagal" adalah sinyal kuat masalah timing, bukan alamat/konfigurasi** — pola all-or-nothing pada pembacaan sekuensial biasanya berarti kurang delay antar-request, bukan salah data.
